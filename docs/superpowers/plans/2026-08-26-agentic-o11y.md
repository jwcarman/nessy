# Agentic Observability Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every turn segment, model call, tool execution and wait is a Micrometer `Observation` named and attributed per the OTel GenAI semantic conventions, exported by whatever the application plugs into `HarnessConfig.observationRegistry(...)`.

**Architecture:** One harness-level fact stream — the fold's output, `(agentId, event, transition | ignored)` — published by BOTH fold sites (`DefaultAgent.deliver`, `DeliveryWorker.fold`) and subscribed to by `HarnessObserver`s via `Harness.subscribe`; one seam `HarnessConfig.observationRegistry(...)`; a package-private `Observations` subscriber that opens/closes segment and wait observations from the stream; `chat` instrumented inside `ProviderModelCallExecutor` (the only place `Usage` exists) and `execute_tool` inside `RegistryToolCallExecutor.run`.

**Tech Stack:** Micrometer Observation 1.16 (`micrometer-observation`, `micrometer-observation-test`), Java 25, JUnit 6, AssertJ, hand-written fakes.

**Spec:** `docs/superpowers/specs/2026-08-26-agentic-o11y-design.md` (binding).

## Global Constraints

- `nessy-agent` gains no dependency beyond `micrometer-observation` (main) and `micrometer-observation-test` (test). No OTel, no exporter, no registry implementation in any `nessy-*` module.
- Names and attributes exactly as spec §1 — `gen_ai.*` from semconv, `nessy.*` only where listed. High-cardinality values (agent id, conversation id, tool call id) are high-cardinality key-values, never low-cardinality tags.
- No new public types. Public additions/changes are exactly: `HarnessConfig.observationRegistry(ObservationRegistry)`; `Harness.subscribe(HarnessObserver)`; `HarnessObserver`'s six methods gain a leading `AgentId`; `Harness.of(...)` swaps `agentObserverFactory` for the registry; `ProviderModelCallExecutor` and `RegistryToolCallExecutor` constructor parameters; `ModelProvider.name()` overrides in the provider modules.
- Registry absent ⇒ `ObservationRegistry.NOOP`; the existing suite must pass unchanged with no test touched for that reason.
- No `@SuppressWarnings`; no star imports; sealed switches exhaustive, no `default`; S5778; S5841; no mocking library.
- Warm scoped builds while iterating; `./mvnw -q clean verify` once per task; one Maven process; `./mvnw license:format -Plicense && ./mvnw spotless:apply` before each commit.

Segment rules (spec §2), implemented in `applied(id, event, transition)` from the event and `transition.next()`:
- `Observed` applied while no segment is open → open `invoke_agent {agentType}` (low-cardinality: `gen_ai.operation.name`, `gen_ai.agent.name`; high-cardinality: `gen_ai.agent.id`, `gen_ai.conversation.id`).
- Any event applied while no segment is open (a delivery resuming the scope) → open one the same way.
- `transition.next()` is `Idle` → close with `nessy.turn.outcome=complete`, or `failed` when the folded event was a `ModelFinished(Failed)`.
- `ApprovalDeferred` applied → open `nessy.approval.wait {tool}` as a child of the segment, keyed by callId; if after this fold no call in `AwaitingTools` is `Running` or `Pending`, close the segment with `nessy.turn.outcome=parked`.
- `ApprovalAnswered` applied → close that wait with `nessy.approval.answer`.
- `ToolDeferred` applied → open `nessy.tool.wait {tool}`; same parked rule.
- `ToolFinished` applied with a present id → close that wait with `nessy.tool.outcome`.
- `ignored(event)` → nothing.
- `reFired(effects)` → `nessy.effects.refired` counter, `+effects.size()`.

Waits and segments are `Observation.start()`ed and `.stop()`ed explicitly — never `observe(Runnable)` — because they span threads. `chat(...)` and `executeTool(...)` create child observations with `parentObservation(openSegment)` when one is open, else parentless. Counters via `registry`'s `ObservationRegistry` cannot count; hold a `MeterRegistry`? — NO: keep to Observation only. Counters are Observations too: `nessy.delivery.dropped` etc. are zero-duration observations started and stopped in place, with the agentType tag; Micrometer's handler yields a count. Document this in `Observations`' javadoc.

- [ ] **Step 3: the stream (spec §3).** The harness owns one fact stream. Read `Harness.observerFor(AgentId)` (`:304`), `agentObserverFactory` and `TurnFanout` first. Then: `Harness` holds the subscribers the way `TurnFanout` holds turn subscribers — a `CopyOnWriteArrayList<HarnessObserver>` (no new public noun; a package-private holder named in `TurnFanout`'s vocabulary is fine) plus the per-id stamping the default narrating observer needs (`observerFor(id)` today stamps the DEFAULT observer per id; keep that behaviour by having the default subscriber stamp the id from the `agentId` it is handed). `HarnessObserver`'s methods gain the `AgentId` as first parameter (`applied(AgentId, AgentEvent, Transition)`, `ignored(AgentId, AgentEvent)`, `applyFailed(AgentId, AgentEvent, RuntimeException)`, `reFired(AgentId, List<Effect>)`, `renderFailed(AgentId, Object, RuntimeException)`, `observationRequeued(AgentId, Object)`) — it is a harness-level subscriber now, not a per-scope object. `Harness.subscribe(HarnessObserver)` overload beside the `TurnObserver` one; subscribers are isolated (throw logged, never propagated — mirror the turn-subscriber isolation). `Harness.of` loses `agentObserverFactory`; `HarnessConfig.harnessObserver(...)` subscribes the configured observer (default: the narrating one) at build. `DefaultAgent` publishes through `harness.facts()` (package-private accessor; pick the name that matches `TurnFanout`'s vocabulary) instead of holding an observer. Update every `HarnessObserver` implementation in tests (grep `implements HarnessObserver` and `HarnessObserver.noop`).

- [ ] **Step 5: `chat`.** `ProviderModelCallExecutor` gains `ObservationRegistry`-backed access via `Observations` (constructor takes `Observations` and the provider name; `HarnessConfig` passes `provider.name()` — find where the provider is resolved, `effectiveModel` ~:453, and keep the `ModelProvider` in hand). Emit `gen_ai.client.token.usage` as two zero-duration observations (token.type input/output) carrying the counts as a high-cardinality value? — NO: token usage must be a histogram of counts, which an Observation cannot record. RULING for the implementer: `gen_ai.client.token.usage` requires a `MeterRegistry`; `ObservationRegistry` alone cannot record a value histogram. Therefore `Observations` accepts an `Optional<MeterRegistry>` discovered from the `ObservationRegistry`'s handlers is NOT possible either. Resolve as: `HarnessConfig.observationRegistry(ObservationRegistry)` stays the seam; token usage rides the `chat` observation as high-cardinality key-values (`gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`) — visible on the span — and the `gen_ai.client.token.usage` metric is produced by the APPLICATION's `ObservationHandler` (a ten-line handler in the example module reads the two key-values on `onStop` and records to its `MeterRegistry`). Write this into spec §1.2 as an amendment in Task 2 and say so in the report. Duration histograms need no such thing: Micrometer's `DefaultMeterObservationHandler` times every observation.
